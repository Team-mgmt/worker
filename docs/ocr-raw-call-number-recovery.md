# OCR 원문 청구기호 복구

## 문제

원격 OCR은 `사계결 1318 문고 102 청눈이 내R 진 희 장편소설 노원정보 문학
813.6 98ㅊ 800`을 읽었지만 구조화 응답의 `ocr_call_number`는 `null`이었다.
기존 파서는 도서기호가 한글로 시작하는 일반 형태(`진98ㅊ`)만 인정했기 때문에 OCR이
선두 한글을 누락한 `98ㅊ`을 청구기호로 분리하지 못했다. 그 결과 KDC 후보 검색과
0건 후보 fallback 모두 실행할 근거가 사라졌다.

## 변경

- `813.6 98ㅊ`처럼 선두 한글이 누락된 도서기호도 OCR 복구 형태로 파싱한다.
- 뒤에 있는 서가 분류 라벨 `800`은 청구기호에 포함하지 않는다.
- `진 희 장편소설`처럼 저자명이 띄어 인식된 경우 `진희`로 복구한다.
- Modal 응답에서 `call_number`가 비어 있으면 EC2 워커가 `raw_text`를 다시 파싱한다.
- 복구 결과는 기존 KDC 후보 검색과 후보 0건 완화 검색에 그대로 전달한다.

Modal 컨테이너를 다시 배포하지 않아도 EC2 워커의 응답 후처리에서 적용된다. 다만
Modal 앱을 나중에 다시 배포하면 동일 파서가 원격 추론 단계에도 반영된다.

## 안전성

숫자로 시작하는 도서기호 복구는 세 자리 KDC 번호 바로 뒤에서만 허용한다. 복구된
불완전 도서기호 때문에 완화 검색이 실행된 후보는 기존 정책대로 자동 정상 확정하지
않고 `검수 필요`로 남긴다.
