# OCR 원문 청구기호 복구

## 문제

원격 OCR은 `사계결 1318 문고 102 청눈이 내R 진 희 장편소설 노원정보 문학
813.6 98ㅊ 800`을 읽었지만 구조화 응답의 `ocr_call_number`는 `null`이었다.
기존 파서는 도서기호가 한글로 시작하는 일반 형태(`진98ㅊ`)만 인정했기 때문에 OCR이
선두 한글을 누락한 `98ㅊ`을 청구기호로 분리하지 못했다. 그 결과 KDC 후보 검색과
0건 후보 fallback 모두 실행할 근거가 사라졌다.

## 변경

- `813.6 98ㅊ`처럼 선두 한글이 누락된 도서기호도 OCR 복구 형태로 파싱한다.
- 뒤에 있는 서가 분류 라벨 `800`은 청구기호에 포함하지 않는다.
- `진 희 장편소설`처럼 저자명이 띄어 인식된 경우 `진희`로 복구한다.
- Modal 응답에서 `call_number`가 비어 있으면 EC2 워커가 `raw_text`를 다시 파싱한다.
- 복구 결과는 기존 KDC 후보 검색과 후보 0건 완화 검색에 그대로 전달한다.

Modal 컨테이너를 다시 배포하지 않아도 EC2 워커의 응답 후처리에서 적용된다. 다만
Modal 앱을 나중에 다시 배포하면 동일 파서가 원격 추론 단계에도 반영된다.

## 안전성

숫자로 시작하는 도서기호 복구는 세 자리 KDC 번호 바로 뒤에서만 허용한다. 복구된
불완전 도서기호 때문에 완화 검색이 실행된 후보는 기존 정책대로 자동 정상 확정하지
않고 `검수 필요`로 남긴다.

## 실제 서버 검증

2026년 8월 15일 노원중앙도서관 관리자 분석에서 수정 전 35번 책의 결과는 다음과
같았다.

```text
OCR 원문: 사계결 1318 문고 102 청눈이 내R 진 희 장편소설 ... 813.6 98ㅊ 800
구조화 제목: 사계결 1318 문고 102 청눈이 내R 진 희 장편소설 813.6 98ㅊ 800
구조화 청구기호: null
DB 후보: 0건
```

수정 배포 후 동일 이미지를 다시 분석한 서버 로그는 다음과 같다.

```text
[matching] relaxed candidate fallback order=35 class='813.6' rows=1500
2026-08-15 12:27:33 [analyze_vision] matching done elapsed=3.1s provider=remote
```

이는 OCR 원문에서 `813.6 98ㅊ`을 구조화 청구기호로 복구하고, 불완전한 도서기호로
인한 0건 검색을 감지한 뒤 `813.6` 후보군까지 확장했음을 의미한다. 즉 TF-IDF와
RapidFuzz가 비교할 DB 후보가 없는 retrieval failure를 해소했다.

같은 fallback 로그가 한 요청에서 두 번 보일 수 있다. 첫 번째는 화면에 반환할 실제
매칭이고, 두 번째는 S3에 네 전략 비교 결과를 기록하는 shadow comparison이다.

## 성능 영향과 후속 개선

해당 실행의 관리자 매칭 시간은 약 1.7초에서 3.1초로 증가했다. KDC `813.6` 후보를
최대 1,500건까지 비교하기 때문이다. 정확도 검증 후에는 복구된 저자 `진희`, 도서기호
끝부분 `98ㅊ` 등을 보조 조건으로 사용해 fallback 후보군을 줄일 수 있다. 단, OCR 오류로
정답 후보가 다시 누락되지 않도록 GT 기반 Top-1·Top-3 평가 후 적용해야 한다.
